APPROVED POLICY IMPLEMENTATION

1. Rating configuration
   - Glicko-2 defaults: rating 1500, RD 350, volatility 0.06, tau 0.5.
   - Placement RD hypothesis: 350/sqrt(number of valid samples), configurable
     through initial RD or the explicit five-value curve. Invalid/abandoned
     attempts are not samples. The curve is not a production calibration.
   - Existing tier cutoffs, earned placement calibration, XP, presence, and
     invitation settings remain unchanged.
   - Environment settings: ARENA_GLICKO_DEFAULT_RATING, ARENA_GLICKO_INITIAL_RD,
     ARENA_GLICKO_DEFAULT_VOLATILITY, ARENA_GLICKO_TAU, ARENA_GLICKO_EPSILON,
     ARENA_GLICKO_PLACEMENT_RD_BY_COUNT. The latter must strictly decrease.
   - Unset/null rating falls back to the configured default; an actual zero
     rating is preserved. A default does not grant an unplaced user earned MMR.
   - Existing transaction/unique settlement guards continue to ensure one rating
     update per finalized match. Current runtime remains two-sided; the one-sided
     2.1 path is not yet implemented.

2. Existing-user preservation and migration
   - Only new ARENA2 placement contexts from the current placement process can
     seed new competitive MMR. Legacy INITIAL scores and tiers are not converted.
   - Previously valid general matches count toward the three-match unlock.
     Eligibility requires a clear, settled normal SUB match, both participants'
     submitted attempts, and original uploaded evidence tied to those attempts.
     Forfeits, automatic endings, incomplete evidence, misattribution, and invalid
     records are excluded. Existing XP accounting is not recalculated.
   - Operator migration archives legacy User tier/rank fields, RankingProfiles,
     ArenaStandings, and the previous competitive profile. It requires fresh
     placement and preserves XP. An account with new rated matches is not reset.
   - Global preflight refuses cutover with in-flight legacy matches, participant
     locks, reserved assets, unresolved paybacks/refunds/reviews, unevaluated paid
     cycles, pending legacy invitations, or incomplete shop purchases.
   - Financial preservation fingerprints cover 13 financial/economy collections
     plus embedded encrypted payback account profiles. Shared finance ledgers
     remain covered even in user-scoped audits. Only hashes/counts are emitted.
   - No financial record is cancelled, overwritten, deleted, marked paid, or
     transferred by migration. Existing operator workflows must reconcile actual
     obligations first. Missing source records cannot be safely auto-repaired.

3. Placement recovery
   - Partial server finalization failures do not consume a slot. Recovery is
     server-triggered, audited, and preserves original attempt/answer documents.
   - Active attempts remain resumable. User abandonment/disqualification consumes
     a slot, not a valid sample. No client error claim restores an attempt.
   - Five exhausted attempts with no valid sample produce operator-review state
     and an AdminTodo. They do not grant an extra attempt or an unearned tier.
   - POST /admin/arena-users/:userId/placement/reset requires existing login/admin
     middleware plus an active admin checked in the database, string request ID,
     and review reason. Transactional adjustments preserve original history.
     Concurrent duplicate resets replay once; subsequent contexts never collide
     with the five previous attempts. A finalized/active/earned-MMR profile cannot
     be reset using this exhausted-attempt endpoint.

4. Availability and forfeits
   - Three shared availability helpers now make Sunday start/upload/cutoff checks
     agree on 24/7 availability. Stored legacy deadlines are not rewritten.
   - Ordinary start/evidence deadlines, operator restrictions, anti-cheating,
     uploads, and verification remain intact.
   - Voluntary forfeits are rejected once evidence submission begins, including
     after upload and after normal settlement. Earlier forfeit retries retain
     their original idempotent behavior. No additional forfeits were enabled.

5. 2.1 candidate scorer (foundation only)
   - Z = (sum(x_i)-sum(p_i))/sqrt(sum(p_i*(1-p_i))), computed on the server from
     five individual correctness/source-rate observations. Exact observations,
     P, V, Z, solve time, algorithm version, and threshold are returned for audit.
   - Z comparison takes priority. Solve time applies only within an explicitly
     supplied closeScoreThreshold. There is NO production threshold default.
   - Missing/non-numeric/extreme p, percentage values accidentally supplied as
     decimals, or unstable variance are refused. No silent smoothing/imputation.
   - Missing/invalid required time returns an explicit unrated INVALID result
     in this candidate implementation. That fail-closed candidate boundary and
     the close-score threshold still require production policy validation.
   - Result explanations use only computed counts, score comparison, and time
     rules. No official answers/model solutions are returned by the scorer.
   - The simulations reuse this scorer, not a duplicate formula. Runtime upload
     and verification integration must still be implemented without changing
     protected detection/upload logic.

DATABASE CHANGES SINCE THE 2.0 HANDOFF

Two new collections, NOT applied to staging/production:
   arenaplacementattemptadjustments: unique attemptId, immutable recovery/reset
     audit fields, user/request indexes; original attempts remain untouched.
   arenamigrationuserarchives: unique userId, immutable legacy/profile snapshots,
     operator identity, valid-general count and financial fingerprint.

ArenaCompetitiveProfile adds legacyNormalMatchesCompleted,
placementProcessVersion, and placementProcessStartedAt. Historical assessment
and financial schemas are unchanged. The original six 2.0 collections remain
documented in GOAT_ARENA_2_0_IMPLEMENTATION_REPORT.txt.

Index tool: read-only by default; --apply is staging-only. It creates/verifies
11 model index sets, never syncs/drops unrelated indexes. Staging must have a
different configured database identity; changed URI credentials/options are not
proof of isolation. Host aliases still require operator verification and a
credential restricted to staging.

Staging migration tool: ARENA_STAGING_DB required, no operating DB fallback;
apply requires --confirm=MIGRATE_ARENA_STAGING, ARENA_STAGING_WRITES_QUIESCED=1,
one explicit user/admin, a clean global drain, and an authorized admin account.
This is an explicit one-user staging operation, not an automatic bulk migration.
Full-volume transaction duration, batching, backups, rollback and exclusive
cutover coordination require staging verification. Repeated hash scans and a
same-snapshot comparison alone cannot prove preservation against other writers.

SIMULATION RESULTS / UNVALIDATED ASSUMPTIONS

Raw executed output: GOAT_ARENA_ASYNC_SIMULATION_RESULTS.json, verified to match
the command output. 10 deterministic seeds, 90 synthetic players, seven
scenarios, 10000 games each: 700000 one-sided rating updates. Historical ratings
and owner profiles stay unchanged; each consumed record creates one new record.
168 existing exact source accuracy rates were used; censored/missing values
were not silently converted to exact probabilities.

Same-pool, equal-ability different-set test: 50000 pairs, 50.08% win share.
Deliberately mismatched hard/easy sets: 50000 pairs, 45.67% harder-set win share,
even though both mean Z values are near zero. This stress distribution is not
the existing pack-generation policy. It demonstrates why unbiased mean Z alone
does not establish fair five-question outcomes across different packs.

Mean MMR drift across 10 runs:
   honest pre-match snapshot: +20.7752 (individual range -3.7179 to +49.7585)
   post-match snapshot sensitivity: +0.5552 (NOT an approved policy change)
   experimental close-score threshold 0.1: +6.3314
   experimental close-score threshold 0.2: +5.9273
   positive cohort shift: +36.5520
   negative cohort shift: -7.2793
   illicit best-of-three record-selection stress: +73.3624

Thresholds/cohort shifts/time distributions are synthetic sensitivity inputs,
not approved production constants. The illicit retry scenario is not an enabled
feature. Simulations assume independent question outcomes and one consumed
record immediately replaced by one valid result; real verification latency,
pool depletion, repeated-owner abuse, transformed skeleton difficulty and real
cohort calibration remain unvalidated. productionValidated is explicitly false.

4. Test authenticated gameplay, timing/reconnect/timeout/review/forfeit races and
   mobile browsers/actual devices against staging, not just static preview data.
5. Upload/retrieve real stored solutions, validate retention and authenticated
